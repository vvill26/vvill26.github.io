这周，Anthropic 平台工程负责人 Katelyn Lesse 介绍了团队把 Claude Messages API 从 Python 单体服务整体迁移到 Rust 的过程。项目启动时团队里没有一位 Rust 工程师，大部分代码由 Claude 完成。数字很亮眼，但更值得看的是：人不再写代码之后，具体在做什么。这一点和今后 AI 芯片编译器与工具链的开发方式高度相关。

## 要点速览

<div class="glance" markdown="1">

**当 AI 承担大部分编码，瓶颈就从「写代码」转移到「证明代码是对的」。**

- **发生了什么：** 一个生产级 API 从 Python 整体移植到 Rust，实现主要由 AI 完成；人负责架构、迁移计划和验证。公开的结果：CPU 消耗下降约 40%–50%，首 token 延迟改善约 10%–20%。
- **分工：** 人是大脑（规格、架构、等价性证明），AI 是双手（具体实现）。
- **对 AI 芯片编译器：** 先建差分测试框架；重新考虑过去一直回避的重写；自动跟进快速变化的上游；把确定性硬件当作给 agent 的干净信号。
- **对内部开发用的 agent：** 把「大脑」（harness、状态、凭据）和「双手」（运行生成代码的沙箱）分开。

</div>

## 一、发生了什么

10 月 27 日，Lesse 在 [Latent Space 播客](https://latent.space/p/how_anthropic_ships_the_1_llm_in_the_world_safely_separating_the_brain_from_the_hands/)里讲了这个项目；前一天她还在 X 上发了一篇[长文](https://x.com/katelyn_lesse/status/2114542280535318557)，讨论 agent 带来的新工程问题。这次移植的大致过程：

- **为什么：** CPU 容量成了约束，而 Python 单体服务很耗 CPU。从技术上看 Rust 是显而易见的选择，但团队里没人会 Rust。
- **怎么做：** 人负责系统设计和迁移计划，具体实现主要交给 Claude。项目被严格限定为一次*移植*：不加新功能。其他团队仍在给 Python 版本加功能，于是用静态分析标出每一个需要在 Rust 版本中同步实现的改动。
- **怎么验证：** 影子流量。新的 Rust 服务接收和 Python 服务相同的请求，对比两边输出，再逐步把真实流量切过去。
- **结果（据其介绍）：** CPU 消耗下降约 40%–50%，首 token 延迟改善约 10%–20%，运行时间更长的负载改善更大。

Lesse 也提到，放在过去她绝不会让团队用这种方式迁移。这种规模的重写通常要拆成很多块、花好几年逐步迁移。她早先的一篇文章 [《You can't avoid the hard part》](https://www.katelynlesse.com/blog/you-cant-avoid-the-hard-part)讲了背后的思路：如果最难的那部分绕不开，就正面去做，而不是选一条看似安全、其实只是推迟失败的路。AI 改变的，是哪些「大动作」变得负担得起。

## 二、真正的变化：人是大脑，AI 是双手

性能提升本身并不意外。从 Python 换到 Rust，不用 AI 也能省下大量 CPU。新的地方在于：一个没有 Rust 经验的团队，用大约一年完成了整体重写，关键是想清楚了哪些事仍然必须由人负责：

- **架构。** 这本质上还是一个分布式系统，形态要由人来定。
- **「完成」的定义。** 「和旧系统行为完全一致」必须被精确化。
- **等价性证明。** 要有一套机制，在真实输入上证明新系统和旧系统一致。
- **范围纪律。** 移植完成之前，对新功能说不。

其余部分都交给「双手」。一句话：**代码变便宜了，证明没有。** 这个团队真正的产出，是计划和验证体系。

## 三、对 AI 芯片编译器和工具链意味着什么

芯片软件栈里，类似这次移植的工作随处可见：大量代码需要重写、换目标平台，或者和别的东西保持同步。六点启示：

**1. 差分测试就是你的影子流量。** 对编译器来说，「对比 Python 和 Rust 的输出」对应的是：用参考实现（PyTorch eager 或 GPU）和自己编译的结果跑同样的输入。再加上随机计算图和形状的 fuzzing，并事先约定每个算子的数值容差。在让 AI 动后端之前，先把这套框架搭起来。没有它，AI 写的编译器代码是负债；有了它，才是杠杆。

**2. 过去一直回避的重写，可以重新考虑。** 每个芯片团队都有一些「从来不值得做」的项目：把后端迁到 MLIR，而不是继续修补旧 IR；把 host 端运行时或推理服务的胶水代码从 Python 换成 Rust 或 C++；为新一代芯片一次性移植整个 kernel 库；用更快的语言重写性能模型或模拟器。用同样的纪律：冻结功能，新旧并行运行，对比，切换。

**3. 自动跟进快速变化的上游。** vLLM 和 SGLang 每周都在变。让 Python 和 Rust 保持同步的静态分析思路在这里同样适用：每次 rebase，由 CI 对比新增的算子、模型结构和调度功能与后端已覆盖的部分，标出缺口，再由 agent 起草缺失的实现供人审阅。

**4. 确定性硬件给 agent 一个干净的信号。** Agent 靠反复尝试和测量来改进。在确定性、编译器静态调度的芯片上，模拟器能给出精确的周期数，agent 搜索 tiling、调度和内存布局时，每次尝试都能得到没有噪声的评分。而在动态调度的硬件上，每次测量都需要多次运行再做统计。

**5. 评测比你想的要多，而且从简单开始。** Lesse 的建议是，多数团队需要的评测比预期多；常见的错误是一直在比较评测框架，结果一个评测也没建起来。对编译器来说，第一版可以是一套按负载固定的测试集，覆盖正确性、性能和编译时间，在 agent 的每次改动上运行。

**6. 关注 host 端 CPU。** Anthropic 这次移植的起因就是 CPU 成本。推理服务在 host 端也有同样的问题：加速器越快，每个 token 的时间里花在 Python 调度和簿记上的比例就越大。值得在它出现在 benchmark 里之前先测清楚。

## 四、字面意义上的「大脑与双手」：内部开发 agent 的基础设施

「大脑与双手」也是 Anthropic 对其 agent 架构的描述。在 [Claude Managed Agents](https://anthropic.com/engineering/managed-agents) 中，harness 和会话状态（大脑）运行在可信的服务器上，生成的代码则在可随时销毁的沙箱（双手）里执行。凭据保存在独立的 Vault 中，只在请求离开沙箱时由代理注入，沙箱里的代码永远看不到。这个设计最初是为了解决延迟和可靠性问题，Lesse 现在则认为安全性才是它最重要的好处。

对一个运行内部编程 agent 的芯片软件团队来说，可以直接对应：

- **生成的代码在沙箱里运行**，模拟器或真实硬件作为工具接入。
- **凭据、工具许可证和保密 IP 留在沙箱外**，通过受控网络访问的代理使用。
- **对运行数小时的 agent 任务做链路追踪，并保留紧急停止开关。**
- **提前规划 CPU 容量。** 编译和仿真都很吃 CPU，负载会随 agent 数量增长。

## 五、几点保留

- **数字是自述的**，没有公开测量方法和基线。Rust 在 CPU 上胜过 Python，本来就在预期之内。
- **相关性错误。** 如果代码和测试都由 AI 写，二者可能共享同一个误解。参考实现要保持独立：由人编写、来自规格，或来自另一套实现。
- **审阅会成为新的队列。** 当 agent 产出的代码多出十倍，人工审阅就是瓶颈，这会推动团队采用更多自动化检查。
- **背景。** 讲述者负责的正是她所介绍的平台。架构是公开的，也被广泛讨论，但经验来自一家公司。

## 结语

AI 芯片的编译器一直靠两件事来评判：跑得对，跑得快。随着 AI 承担越来越多的编写工作，真正会积累的，是证明这两点的基础设施：参考实现、差分测试、确定性模拟器和评测集。先建好这些的团队，才能用 AI 去做别人一直在推迟的那些大规模重写。
