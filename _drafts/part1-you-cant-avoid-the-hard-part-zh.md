*「AI 时代的芯片软件」系列第一篇，共三篇。*

想象一场小范围的工程师 offsite。摆在他们面前的项目，之前已经有团队尝试过、卡住过。Stripe 希望一个用户在所有产品里只有一个账户：同一家企业，可能既在付订阅费，又在收款，还在接收转账，用同一份余额结算。现有的数据模型表达不了这件事。客户、商户、收款方分别是不同的对象，而公司里几乎所有支付和计费 API 都是围绕这些对象写的。

Katelyn Lesse 现在是 Anthropic 平台工程负责人，当时在 Stripe Connect 工作。她在今年 7 月的文章 [《You can't avoid the hard part》](https://www.katelynlesse.com/blog/you-cant-avoid-the-hard-part)里讲了这个故事。

既定方案是最「负责任」的那种：在旧模型旁边建新的账户模型，双向同步，现有代码不用改。放在幻灯片上，它看起来很安全。可现实是，一家既是商户又是客户的企业，需要三个模型各存一份同样的名称和邮箱，并且永远保持一致。这种同步既脆弱，也无法扩展。

讨论一次次回到一个曾经被否掉的想法，姑且叫它「封装」：在代码库里每一处读写前面放一个统一接口，让所有代码只和新模型打交道。它被否掉的原因，是估算以「工程年」计。于是他们换了一种检验方式：假设最不可能的那部分做成了，计划的其余部分还站得住吗？答案是站得住。决定随之而来：几位被这个问题激发的工程师接手主导，工作集中推进、靠 codemod 驱动；Lesse 也接受了它可能成为整个项目最长那根杆的风险。这项工作最终用了数个工程年，挫折不少。她认为，没有这一步，新账户体系根本无法上线。

第二个时刻发生在多年之后的 Anthropic。她的团队用最简单的方式做出了 Claude Managed Agents 的第一版：每个会话启动一个容器，里面跑 Claude Code，所有东西都在这个容器里。早期客户遇到的是启动慢、容器一挂会话就丢，以及生成的代码就挨着凭据运行。团队一个症状一个症状地修，花了大量时间排查卡住的会话，问题到底出在 harness、事件流还是容器，常常说不清。最后他们看到了唯一的根因：单容器设计本身。解决办法是一个真正的分布式系统，而公开测试版近在眼前。他们问了同一个问题：用旧设计上线，还能成功吗？答案是不能。于是推迟发布，重建。

Lesse 的总结很直接：当最难的部分绕不开时，"the safe path is just delaying failure"——稳妥路线只是在推迟失败。

她的结尾正是这个系列的起点：AI 正在改变哪些问题算「难」。几个工程年的 codemod，或者用一门陌生语言整体重写，现在也许够得着了。[第二篇](/zh/2026/10/humans-brain-ai-hands/)看一个正是这样的重写，以及它对 AI 芯片公司的编译器和工具链意味着什么。[第三篇](/zh/2026/11/agent-infra-chip-startup/)讨论一家小型芯片初创公司要用这种方式工作，需要建什么、要花多少钱。
